# Exchange Order — тестовое задание

Проектирование процесса **создания заявки на обмен валют** во внутреннем модуле цифрового кошелька.
Домен — финтех с криптовалютным контуром: фиат и крипто-активы в одном кошельке, обмен между ними.

Исходное задание: [docs/BRD.md](docs/BRD.md), §11 — перечень ожидаемых артефактов.

## Запуск

### Прототип экрана обмена

```bash
cd prototype
npm install
npm run dev          # http://localhost:5173
```

### Документация и API

Два отдельных адреса, оформление по образцу `common_docs` (MkDocs Material):

```powershell
cd portal
npm install
npm run wiki         # http://127.0.0.1:8100/  — wiki с документацией
npm run api          # http://127.0.0.1:8101/  — Swagger UI со спецификациями
```

Или собрать и раздать всё одним сервером:

```powershell
cd portal
npm run build        # -> portal/dist
npm run serve        # http://127.0.0.1:8080/ и http://127.0.0.1:8080/swagger/
```

### Деплой на Railway

Проект упакован в один образ: прототип, wiki и Swagger UI раздаются одним nginx.

```bash
railway login && railway init && railway up && railway domain
```

| Путь | Что отдаёт |
|------|-----------|
| `/` | прототип экрана обмена |
| `/docs/` | wiki с документацией |
| `/docs/swagger/` | Swagger UI |
| `/healthz` | health-check для Railway |

Переменные окружения задавать не нужно — `PORT` приходит от Railway и подставляется в конфигурацию
nginx на старте контейнера. Пошаговая инструкция, проверка успешности деплоя, откат и разбор
типичных отказов — [DEPLOY.md](DEPLOY.md).

---

Wiki рендерит все 13 диаграмм Mermaid, в Swagger UI переключаются 10 спецификаций
(основной API и девять внешних сервисов). Markdown **не копируется** — страницы вики являются
однострочными обёртками над исходниками через `pymdownx.snippets`, поэтому второй копии,
способной разойтись с оригиналом, не существует. Swagger UI и Mermaid подключены локально;
обращение к CDN остаётся только аварийной веткой `onerror`. Подробнее — [portal/README.md](portal/README.md).

Данные захардкожены, авторизации нет, сети нет — по требованию заказчика фокус на экране обмена.
Слой `src/api/` имитирует BFF и все девять внешних сервисов; замена его на `fetch()` — единственное,
что нужно для перехода на реальный бэкенд.

Балансы видны в двух местах: строкой `Available:` в шапке блоков «You Pay» / «You Receive»
и полным списком — в выпадающем списке выбора актива, вместе с пометкой заблокированных средств
и `No funds` у нулевого баланса.

### Демонстрация негативных сценариев

Отказы внешних сервисов включаются параметром URL — на экране нет служебной панели:

| Сценарий | URL | Что произойдёт |
|----------|-----|----------------|
| Happy path | `/` | Заявка создаётся, статус `PENDING` |
| Изменение курса | `/?scenario=RATE_DRIFT` | Через 7 секунд курс уходит на −0.53 %; появляется баннер «было → стало», кнопка блокируется до принятия новых условий |
| Сервис курсов недоступен | `/?scenario=RATES_DOWN` | Котировка не строится, `RATE_SERVICE_UNAVAILABLE`, восстановление — кнопкой Retry |
| Сервис обмена недоступен | `/?scenario=EXCHANGE_DOWN` | Отказ в момент подтверждения, `EXCHANGE_SERVICE_UNAVAILABLE` |
| Верификация не завершена | `/?scenario=KYC_PENDING` | `KYC_PENDING` — комплаенс блокирует раньше проверки баланса |
| Дневной лимит | `/?scenario=LIMIT_HIT` | Крупная сумма даёт `LIMIT_EXCEEDED_DAILY`, мелкая проходит |
| Ручная проверка комплаенса | `/?scenario=SCORING_REVIEW` | Заявка принимается со статусом `MANUAL_REVIEW` — это не ошибка |
| Медленная сеть | `/?scenario=SLOW_NETWORK` | Задержка 2.5 с: видны скелетоны и состояние загрузки кнопки |

Соответствие сценариев feature-файлу и селекторам интерфейса —
[docs/features/README.md](docs/features/README.md) §6.

### Движение курса

Курс не статичен: к базовому значению применяется коэффициент — один раз за каждое истёкшее
окно длиной в TTL котировки. Поэтому по истечении 15 секунд автообновление показывает
**действительно новую** цену, а не то же самое число.

| Параметр URL | По умолчанию | Что делает |
|--------------|--------------|-----------|
| `?rateTickFactor=0.99` | `0.9995` | Коэффициент за окно. По умолчанию −0.05 % — ниже порога вмешательства 0.20 %, поэтому пересчёт тихий |
| `?rateTickMs=3000` | `15000` | Длина окна |
| `?rateTick=off` | — | Замораживает рынок на фикстурных курсах |

Если нужно увидеть требование заново принять условия (BRD §8) — либо `?scenario=RATE_DRIFT`
(−0.53 % через 7 секунд), либо `?rateTickFactor=0.99`, что даёт −1 % за окно.
Подробности и обоснование выбранной величины — [docs/00-canonical-model.md](docs/00-canonical-model.md) §10.3.

## Ключевые решения и их цена

Полный список — [docs/SDD.md](docs/SDD.md) §3 (14 ADR) и [promtlog.md](promtlog.md).
Пять, которые определяют всё остальное:

| Решение | Почему | Цена |
|---------|--------|------|
| Деньги — только десятичные строки, `float` запрещён на всём пути | Двоичное представление теряет точность на суммах вроде `0.1 + 0.2`; в финтехе это невосстановимо | Арифметика через `decimal.js`, нельзя пользоваться обычными операторами |
| Двухфазный протокол `quote → order` | Пользователь подтверждает ровно тот курс, который видел; без фазы котировки курс мог бы измениться между показом и списанием | Нужно отдельное TTL-хранилище котировок и обработка их истечения |
| Комиссия удерживается **внутри** введённой суммы (`INCLUDED_IN_SOURCE`) | Иначе кнопка `MAX` и чип 100 % всегда упирались бы в нехватку средств: `сумма + комиссия > баланс` | Пользователь получает меньше, чем «сумма × курс», поэтому строка `Fee` в сводке обязательна |
| Проверки комплаенса (KYC → лимиты → скоринг) идут **раньше** проверки баланса | Неверифицированный пользователь не должен узнавать состояние чужих балансов и лимитов через различие текстов ошибок | Человек с недостатком средств и незавершённым KYC сначала увидит сообщение про KYC |
| `Idempotency-Key` обязателен для создания заявки | Ретрай `POST` при таймауте без него означает двойное списание | Клиент обязан генерировать и переиспользовать ключ в пределах одной попытки |

## Как это делалось

Работа выполнена мультиагентно. Персоны взяты из [docs/agents/](docs/agents/) и подключены как
subagents в [.claude/agents/](.claude/agents/).

| Агент | Артефакт |
|-------|----------|
| CTO / Orchestrator | Канонический контракт, разрешение конфликтов, приёмка, `promtlog.md` |
| Software Architect | `docs/SDD.md` |
| API Architect | `docs/api/**` |
| Business Analyst | `docs/features/**` |
| UX Researcher + UX Architect + UI Designer | `docs/UX-UI-Spec.md` |

Порядок был такой: оркестратор сначала зафиксировал канонический доменный контракт, и только потом
запустил четырёх агентов параллельно. Без этого шага четыре независимых документа неизбежно
разошлись бы в именах полей, кодах ошибок и правилах округления.

Агенты нашли в исходных документах и в самом каноне **36 расхождений** — все разобраны в
[promtlog.md](promtlog.md) с указанием, кто нашёл, что предложил и что решено. Три примера:

- Дизайн-триада обнаружила, что зелёный `#16A34A`, предписанный обоими брифами, не проходит
  WCAG AA для текста (3.30 при требуемых 4.5). Бриф не был выполнен буквально — цвет разделён
  на заливку и текстовый вариант `#15803D`.
- API Architect обнаружил, что в каталоге ошибок нет кода для «заявка не найдена», и вместо того
  чтобы подставить неточный код, вынес его за закрытый enum и поднял вопрос. Код ратифицирован
  решением O-1 и внесён в канон, спецификацию и прототип.
- Code Reviewer на приёмке нашёл 6 блокеров, которые прошли мимо всех автопроверок, потому что те
  сверяли согласованность документов, а не поведение экрана. Самый серьёзный: `acceptRateChange`
  был реализован обратно контракту и позволял исполнить сделку по курсу, которого пользователь
  не видел. Все шесть исправлены, разбор — в [promtlog.md](promtlog.md) §13.

## Границы работы

**В скоупе:** создание заявки — от открытия экрана до получения `orderId` и статуса `PENDING`.

**Вне скоупа** (по BRD §1 и уточнению заказчика): исполнение заявки, matching на бирже,
бухгалтерские проводки, история операций, ончейн-транзакции, авторизация и сессии.
Девять внешних сервисов **не реализуются** — описано только то, что приложение от них получает.

**Открытые вопросы к заказчику:** восемь пунктов в [promtlog.md](promtlog.md) §11. Каждый имеет
провизорное решение, поэтому ни один не блокирует работу. Наиболее существенные — граница суток
для дневного лимита при резидентстве `AE` (сброс в 04:00 по местному времени) и подтверждение
идемпотентности на стороне сервисов аккаунтинга и заявок.
