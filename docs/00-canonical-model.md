# 00 — Канонический доменный контракт

> **Статус:** нормативный. Подготовлен оркестратором (CTO-001) **до** запуска специализированных агентов.
> Все артефакты проекта (SDD, OpenAPI, Gherkin, прототип) обязаны использовать имена, коды ошибок,
> статусы и правила округления **именно из этого документа**. Расхождение = дефект артефакта.
>
> Источники: `BRD.md`, `Product Context.md`, `Design Brief.md`, `System Design Brief.md`,
> `API Brief.md`, `Gherkin Brief.md` + уточнения заказчика (см. `promtlog.md` §1).

## 1. Скоуп

### В скоупе

Создание заявки на обмен (Exchange Order) из внутреннего кошелька: от открытия экрана
до получения пользователем `orderId` и подтверждения приёма заявки.

### Вне скоупа

Исполнение заявки, matching на бирже, бухгалтерские проводки, вывод/ввод средств,
история операций, ончейн-транзакции, авторизация и сессии.

### Граница скоупа по статусу

Терминальное состояние для этого задания — заявка в статусе **`PENDING`**
(принята, средства зарезервированы, ожидает исполнения). Всё, что дальше, — вне работ.

## 2. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Asset** | Учётная единица баланса: фиат (`RUB`, `EUR`) или крипто (`USDT`, `BTC`, `ETH`). Для крипто уточняется сетью. |
| **Network** | Блокчейн-сеть крипто-актива (`TRON`, `ETHEREUM`, `BITCOIN`). `USDT@TRON` и `USDT@ETHEREUM` — **разные балансы**. |
| **Pair** | Направленная пара `FROM → TO`, например `RUB→USDT`. Пары односторонние: `RUB→USDT` и `USDT→RUB` конфигурируются отдельно. |
| **Quote (котировка)** | Зафиксированный на короткое время расчёт: курс, комиссия, суммы. Имеет `quoteId` и `expiresAt`. |
| **Rate Lock TTL** | Время жизни котировки. **15 секунд** (BRD §4). |
| **Exchange Order** | Заявка на обмен, созданная на основании валидной котировки. |
| **Hold (резерв)** | Блокировка средств на балансе списания на время исполнения заявки. |
| **Available balance** | `total − held`. Все проверки достаточности средств ведутся **только** по available. |
| **Quote drift** | Ситуация, когда курс изменился между построением котировки и подтверждением. |

## 3. Карта внешних систем

BRD §10 перечисляет 4 сервиса, заказчик — 8. После дедупликации получается **9 внешних систем**.
Приложение (Exchange BFF) — единственный, кто их оркеструет; фронтенд ходит только в BFF.

| # | Система | Соответствие BRD | Что приложение получает | Критичность на пути создания заявки |
|---|---------|------------------|--------------------------|--------------------------------------|
| S1 | **Users Service** | — | Профиль, резидентство, статус, тир обслуживания, идентификаторы кошельков | **Blocking** |
| S2 | **KYC Service** (WebID) | — | Уровень и статус верификации, срок действия, разрешённые операции | **Blocking** |
| S3 | **Scoring / AML Service** | — | Risk score, решение `ALLOW / REVIEW / DENY`, причины | **Blocking** |
| S4 | **Limits & Fees Service** | — | Мин/макс суммы по паре, остатки лимитов оборота, схема комиссий | **Blocking** |
| S5 | **Exchange Rate Service** | Exchange Rate Service | Актуальные котировки, TTL, источник цены, признак stale | **Blocking** |
| S6 | **Accounting Service** | Wallet Service | Балансы (total/available/held), создание и снятие холдов | **Blocking** |
| S7 | **Crypto Provider** | — | Данные ордеров/ликвидности с бирж, сетевые комиссии, статус сети | **Degradable** |
| S8 | **Order Service** | Order Service | Регистрация заявки, присвоение `orderId`, статус | **Blocking** |
| S9 | **Notification Service** | — | Подтверждение доставки уведомления о созданной заявке | **Non-blocking** |

`Exchange Service` из BRD §10 — это **не внешняя система**, а сам оркестратор бизнес-проверок
внутри нашего домена (см. SDD). Это осознанная переинтерпретация BRD, зафиксированная здесь.

### Классы критичности

| Класс | Правило |
|-------|---------|
| **Blocking** | Отказ → заявка не создаётся, пользователю показывается ошибка сервиса (`503`). |
| **Degradable** | Отказ → работаем на закешированных/дефолтных данных, помечаем котировку `degraded: true`. |
| **Non-blocking** | Отказ → заявка создана успешно, доставка уведомления уходит в ретрай-очередь. |

## 4. Доменная модель

### 4.1 Asset

```
Asset {
  assetId    : string   // "RUB", "USDT", "BTC" — уникален в пределах кошелька вместе с network
  type       : FIAT | CRYPTO
  network    : string?  // обязателен для CRYPTO: "TRON" | "ETHEREUM" | "BITCOIN"
  decimals   : integer  // RUB=2, EUR=2, USDT=6, BTC=8, ETH=8
  symbol     : string   // "₽", "$", "₿" — только для отображения
  displayName: string
}
```

### 4.2 Balance

```
Balance {
  assetId  : string
  network  : string?
  total    : decimal-string
  held     : decimal-string
  available: decimal-string   // инвариант: available = total − held, всегда ≥ 0
}
```

### 4.3 Quote

```
Quote {
  quoteId        : uuid
  fromAsset      : AssetRef
  toAsset        : AssetRef
  fromAmount     : decimal-string  // полная сумма списания, включая комиссию
  feeAmount      : decimal-string  // в валюте списания
  netFromAmount  : decimal-string  // fromAmount − feeAmount, идёт в конвертацию
  toAmount       : decimal-string  // сумма получения
  rate           : decimal-string  // единиц toAsset за 1 единицу fromAsset
  inverseRate    : decimal-string  // только для отображения
  feePolicy      : FeePolicy
  rateSource     : string          // "AGGREGATED" | "BINANCE" | "CBR" | "INTERNAL"
  quotedAt       : timestamp
  expiresAt      : timestamp       // quotedAt + 15s
  degraded       : boolean         // true, если использованы кешированные данные
}
```

### 4.4 FeePolicy

```
FeePolicy {
  mode        : INCLUDED_IN_SOURCE   // фиксировано, см. §5.3
  percent     : decimal-string       // "0.35" = 0.35 %
  minFee      : decimal-string       // в валюте списания
  maxFee      : decimal-string | null
  networkFee  : decimal-string       // 0 для внутреннего обмена, см. §5.4
}
```

### 4.5 ExchangeOrder

```
ExchangeOrder {
  orderId        : string   // "ord_" + ULID, устойчиво сортируется по времени
  status         : OrderStatus
  quoteId        : uuid
  fromAsset      : AssetRef
  toAsset        : AssetRef
  fromAmount     : decimal-string
  feeAmount      : decimal-string
  toAmount       : decimal-string
  rate           : decimal-string
  holdId         : string   // идентификатор резерва в Accounting
  createdAt      : timestamp
  estimatedCompletionAt : timestamp
  idempotencyKey : string
  correlationId  : string
}
```

## 5. Денежная арифметика

Раздел нормативный. Нарушение = дефект.

### 5.1 Представление

Все денежные величины и курсы передаются и хранятся как **строки с десятичной записью**
(`"25450.00"`, `"0.010638297872"`). Двоичные `float`/`double` **запрещены** на всём пути:
API, BFF, состояние фронтенда, отображение. На фронтенде — `decimal.js` или целочисленные
minor units; `Number` допускается только для не-денежных значений (таймер, проценты чипов).

Регулярное выражение для валидации: `^(0|[1-9]\d{0,18})(\.\d{1,18})?$` (неотрицательное).

### 5.2 Направление курса

`rate` = сколько единиц `toAsset` даётся за **1 единицу** `fromAsset`.
Пример: `RUB→USDT`, `rate = "0.010638297872"` ⇔ `1 USDT = 94.00 RUB`.
`inverseRate = "94.00"` считается BFF и служит **только** для отображения
(«1 USDT = 94.00 RUB» читается человеком легче, чем обратное).

### 5.3 Порядок расчёта и режим комиссии

Режим комиссии — **`INCLUDED_IN_SOURCE`**: комиссия удерживается **внутри** введённой суммы,
а не сверху.

```
1. fromAmount    = ввод пользователя, округлён до decimals(fromAsset)
2. feeRaw        = fromAmount × percent / 100
3. feeAmount     = clamp(feeRaw, minFee, maxFee), округление ВВЕРХ до decimals(fromAsset)
4. netFromAmount = fromAmount − feeAmount
5. toAmountRaw   = netFromAmount × rate
6. toAmount      = округление ВНИЗ до decimals(toAsset)
```

**Почему именно так** (решение оркестратора, конфликт C-06 из `promtlog.md`):
при комиссии «сверху» кнопка `MAX` / чип `100 %` всегда приводили бы к отказу
`INSUFFICIENT_FUNDS`, потому что `fromAmount + fee > available`. Требования BRD §4
(процент от баланса) и Design Brief (`MAX`) несовместимы с режимом `ON_TOP`.
Цена решения: пользователь получает чуть меньше, чем «сумма × курс» — поэтому строка
`Fee` в Exchange Summary обязательна и не может быть скрыта.

### 5.4 Правила округления

| Величина | Режим | Обоснование |
|----------|-------|-------------|
| `feeAmount` | `ROUND_UP` до `decimals(fromAsset)` | Детерминированно и не в убыток системе |
| `toAmount` | `ROUND_DOWN` до `decimals(toAsset)` | Никогда не обещаем пользователю больше, чем сможем выдать |
| `rate` | без округления, как пришёл от S5 | Округление курса ломает воспроизводимость расчёта |
| `inverseRate` | `ROUND_HALF_UP`, 2 знака | Только отображение |

Banker's rounding **не применяется** — недетерминирован для ревизии.

**Инварианты, проверяемые на сервере при создании заявки:**

```
I1: feeAmount + netFromAmount == fromAmount                      (точное равенство)
I2: toAmount ≤ netFromAmount × rate
I3: fromAmount ≤ balance.available(fromAsset)
I4: все величины ≥ 0
I5: decimals(value) ≤ decimals(asset)
```

### 5.5 Сетевая комиссия

Обмен **внутренний**: активы перемещаются между балансами одного кошелька, ончейн-транзакции
не выполняются, поэтому `networkFee = "0"`. Поле и строка `Network` в Exchange Summary
(требование Design Brief) сохраняются, потому что:
1. они показывают пользователю, **в какой сети** он получит крипто-актив (`USDT@TRON`);
2. при последующем выводе средств сеть определяет реальную стоимость — пользователь должен
   осознавать выбор уже на этапе обмена.

## 6. Цепочка валидации

Проверки выполняются сервером **строго в этом порядке**, fail-fast. Порядок нормативен:
он задаёт **детерминированную ошибку**, когда нарушено несколько условий одновременно.

| Шаг | Проверка | Источник данных | Код ошибки при провале |
|-----|----------|-----------------|------------------------|
| 1 | Схема запроса, формат сумм, обязательные поля | локально | `VALIDATION_ERROR` |
| 2 | Идемпотентность: ключ не переиспользован с другим телом | локально | `IDEMPOTENCY_CONFLICT` |
| 3 | Активы существуют и включены | S4 / конфиг | `ASSET_NOT_SUPPORTED` |
| 4 | `fromAsset ≠ toAsset` (с учётом network) | локально | `SAME_ASSET_PAIR` |
| 5 | Пара разрешена к обмену | S4 | `PAIR_NOT_SUPPORTED` |
| 6 | Котировка существует | S5 / quote store | `QUOTE_NOT_FOUND` |
| 7 | Котировка не использована | quote store | `QUOTE_ALREADY_USED` |
| 8 | Котировка не истекла (`now < expiresAt`) | quote store | `QUOTE_EXPIRED` |
| 9 | Параметры запроса совпадают с котировкой | локально | `QUOTE_MISMATCH` |
| 10 | Курс не уехал за допустимый порог | S5 | `RATE_CHANGED` |
| 11 | `fromAmount ≥ minAmount(pair)` | S4 | `AMOUNT_BELOW_MINIMUM` |
| 12 | `fromAmount ≤ maxAmount(pair)` | S4 | `AMOUNT_ABOVE_MAXIMUM` |
| 13 | Пользователь активен, кошелёк не заморожен | S1, S6 | `WALLET_FROZEN` / `USER_BLOCKED` |
| 14 | KYC-уровень достаточен и не истёк | S2 | `KYC_REQUIRED` / `KYC_LEVEL_INSUFFICIENT` / `KYC_PENDING` / `KYC_EXPIRED` |
| 15 | Лимиты оборота (день/месяц) не превышены | S4 | `LIMIT_EXCEEDED_DAILY` / `LIMIT_EXCEEDED_MONTHLY` |
| 16 | Скоринг разрешает операцию | S3 | `SCORING_DENIED` / `SCORING_REVIEW_REQUIRED` |
| 17 | Достаточно доступного баланса | S6 | `INSUFFICIENT_FUNDS` |
| 18 | Резерв (hold) успешно создан | S6 | `HOLD_FAILED` |
| 19 | Заявка зарегистрирована | S8 | `ORDER_CREATION_FAILED` |

### Замечание по порядку 13–17

Проверки соответствия (KYC → лимиты → скоринг) идут **перед** проверкой баланса. Это применение
принципа **Compliance First** (`09-orchestrator.md`): неверифицированный пользователь не должен
узнавать про состояние своих лимитов и балансов через различие сообщений об ошибке — это утечка
информации и вектор перебора. Цена решения: пользователь с недостатком средств и незавершённым
KYC увидит сначала сообщение про KYC. Это приемлемо, потому что KYC блокирует его в любом случае.

**Клиентская предвалидация** (шаги 1, 4, 11, 12, 17) выполняется в прототипе немедленно и inline —
для скорости отклика. Она **не заменяет** серверную: сервер всегда прогоняет всю цепочку заново.

## 7. Каталог ошибок

Единая обёртка ответа об ошибке (RFC 9457 Problem Details, расширенный):

```json
{
  "type": "https://api.wallet.internal/problems/insufficient-funds",
  "title": "Insufficient funds",
  "status": 422,
  "code": "INSUFFICIENT_FUNDS",
  "detail": "Available balance 25450.00 RUB is less than requested 30000.00 RUB",
  "instance": "/v1/exchange-orders",
  "correlationId": "01J9X2C4K7QF8N3M5T6V7W8Y9Z",
  "timestamp": "2026-08-07T10:15:32.117Z",
  "params": { "available": "25450.00", "requested": "30000.00", "assetId": "RUB" },
  "retryable": false
}
```

`code` — **стабильный машиночитаемый контракт**. Фронтенд ветвится только по нему,
никогда по `title`/`detail`.

| `code` | HTTP | Retryable | Куда крепится в UI | Сообщение пользователю (EN) |
|--------|------|-----------|--------------------|------------------------------|
| `VALIDATION_ERROR` | 400 | нет | к полю | `Enter a valid amount` |
| `ASSET_NOT_SUPPORTED` | 422 | нет | селектор | `This asset is not available for exchange` |
| `SAME_ASSET_PAIR` | 422 | нет | селектор | `Select two different assets` |
| `PAIR_NOT_SUPPORTED` | 422 | нет | селектор | `This pair is not available right now` |
| `AMOUNT_BELOW_MINIMUM` | 422 | нет | поле «You Pay» | `Minimum amount is {min} {asset}` |
| `AMOUNT_ABOVE_MAXIMUM` | 422 | нет | поле «You Pay» | `Maximum amount is {max} {asset}` |
| `INSUFFICIENT_FUNDS` | 422 | нет | поле «You Pay» | `Not enough {asset}. Available: {available}` |
| `QUOTE_NOT_FOUND` | 404 | да | баннер | `Rate expired. Refreshing…` |
| `QUOTE_EXPIRED` | 409 | да | баннер | `Rate expired. We updated the quote.` |
| `QUOTE_ALREADY_USED` | 409 | нет | баннер | `This exchange was already submitted` |
| `QUOTE_MISMATCH` | 409 | да | баннер | `Details changed. Please confirm again.` |
| `RATE_CHANGED` | 409 | да | баннер | `Rate changed. Calculation updated.` |
| `KYC_REQUIRED` | 403 | нет | баннер | `Verify your identity to exchange` |
| `KYC_LEVEL_INSUFFICIENT` | 403 | нет | баннер | `Higher verification level required` |
| `KYC_PENDING` | 403 | да | баннер | `Verification in progress` |
| `KYC_EXPIRED` | 403 | нет | баннер | `Your verification has expired` |
| `LIMIT_EXCEEDED_DAILY` | 422 | нет | поле «You Pay» | `Daily limit reached. Available today: {remaining}` |
| `LIMIT_EXCEEDED_MONTHLY` | 422 | нет | поле «You Pay» | `Monthly limit reached` |
| `SCORING_DENIED` | 403 | нет | баннер | `Operation declined. Contact support.` |

| `HOLD_FAILED` | 409 | да | баннер | `Could not reserve funds. Try again.` |
| `IDEMPOTENCY_CONFLICT` | 409 | нет | баннер | `Conflicting request` |
| `ORDER_CREATION_FAILED` | 500 | да | баннер | `Something went wrong. Try again.` |
| `RATE_SERVICE_UNAVAILABLE` | 503 | да | баннер | `Rates are temporarily unavailable` |
| `EXCHANGE_SERVICE_UNAVAILABLE` | 503 | да | баннер | `Exchange is temporarily unavailable` |
| `UPSTREAM_TIMEOUT` | 504 | да | баннер | `Request timed out. Try again.` |
| `RATE_LIMITED` | 429 | да | баннер | `Too many requests. Slow down.` |
| `ORDER_NOT_FOUND` | 404 | нет | баннер | `Order not found` |

`ORDER_NOT_FOUND` добавлен позже остальных: пробел обнаружил API Architect при проектировании
`GET /v1/exchange-orders/{orderId}` и, вместо того чтобы подставить неточный код, вынес вопрос
наверх. Решение O-1 оркестратора (`promtlog.md` §9) — ратифицировать. Код лежит вне цепочки §6:
он относится к чтению заявки, а не к её созданию.

`SCORING_REVIEW_REQUIRED` возвращается с `202 Accepted` и телом заявки в статусе
`MANUAL_REVIEW` — это **не ошибка**, а альтернативный успешный исход.

## 8. Жизненный цикл заявки

```
                 ┌──────────┐
                 │  DRAFT   │  только на клиенте, не существует на сервере
                 └────┬─────┘
                      │ POST /exchange-orders
                      ▼
              ┌───────────────┐
        ┌─────┤  VALIDATING   ├─────┐          внутреннее, наружу не отдаётся
        │     └───────┬───────┘     │
        │             │             │
   отказ проверок     │ ok      скоринг = REVIEW
        ▼             ▼             ▼
  ┌──────────┐  ┌──────────┐  ┌──────────────┐
  │ REJECTED │  │ PENDING  │  │ MANUAL_REVIEW│
  └──────────┘  └────┬─────┘  └──────┬───────┘
   терминальный      │               │ решение комплаенса
                     │        ┌──────┴──────┐
   ══════════════════╪════════╪═════════════╪══════ ГРАНИЦА СКОУПА ЗАДАНИЯ
                     ▼        ▼             ▼
              ┌────────────┐        ┌──────────┐
              │ EXECUTING  │        │ REJECTED │
              └─────┬──────┘        └──────────┘
          ┌─────────┼─────────┐
          ▼         ▼         ▼
   ┌───────────┐ ┌────────┐ ┌─────────┐
   │ COMPLETED │ │ FAILED │ │ EXPIRED │
   └───────────┘ └────────┘ └─────────┘
```

| Статус | Отдаётся наружу | Средства | Терминальный |
|--------|-----------------|----------|--------------|
| `PENDING` | да | зарезервированы (hold) | нет |
| `MANUAL_REVIEW` | да | зарезервированы | нет |
| `REJECTED` | да | не тронуты / hold снят | да |
| `EXECUTING` | да | зарезервированы | нет |
| `COMPLETED` | да | списаны и зачислены | да |
| `FAILED` | да | hold снят | да |
| `EXPIRED` | да | hold снят | да |

## 9. Соглашения REST API

| Аспект | Решение |
|--------|---------|
| Базовый путь | `/v1` — версия в пути, ломающие изменения = новый major |
| Формат | `application/json; charset=utf-8`; ошибки — `application/problem+json` |
| Идемпотентность | Заголовок `Idempotency-Key` (UUIDv4) **обязателен** для `POST /exchange-orders`; окно хранения 24 ч; повтор с тем же телом → тот же `201`-ответ, с другим телом → `409` |
| Трассировка | `X-Correlation-Id` — принимаем от клиента, генерируем при отсутствии, возвращаем в каждом ответе и в каждой ошибке |
| Именование | Ресурсы — множественное число, `kebab-case` в путях, `camelCase` в JSON |
| Время | ISO-8601 UTC с миллисекундами, суффикс `Z` |
| Деньги | всегда строки (см. §5.1) |
| Пагинация | cursor-based (`cursor`, `limit`) — для списков вне скоупа |
| Rate limiting | `X-RateLimit-Limit` / `-Remaining` / `-Reset`, превышение → `429` |
| Аутентификация | В контракте описана (`Bearer` JWT + `X-User-Id` от gateway); **в прототипе не используется** по требованию заказчика |

## 10. Хардкод-фикстуры прототипа

Единственный источник правды для моков. Прототип не ходит в сеть.

### 10.1 Пользователь

```
userId       : "usr_01J8ZQ4H9K2M3N4P5R6S7T8V9W"
displayName  : "Alex Morgan"
residency    : "AE"
tier         : "TIER_2"
status       : "ACTIVE"
kycLevel     : 2  (VERIFIED)
kycValidUntil: 2027-04-30T23:59:59.000Z   // конец дня: верификация действует весь последний день
riskScore    : 17  (LOW → ALLOW)
```

### 10.2 Активы и балансы

| assetId | type | network | decimals | total | held | available |
|---------|------|---------|----------|-------|------|-----------|
| `RUB` | FIAT | — | 2 | `25450.00` | `0.00` | `25450.00` |
| `USDT` | CRYPTO | `TRON` | 6 | `135.270000` | `0.000000` | `135.270000` |
| `BTC` | CRYPTO | `BITCOIN` | 8 | `0.01420000` | `0.00000000` | `0.01420000` |
| `ETH` | CRYPTO | `ETHEREUM` | 8 | `0.86000000` | `0.10000000` | `0.76000000` |
| `EUR` | FIAT | — | 2 | `0.00` | `0.00` | `0.00` |

`ETH` намеренно имеет ненулевой `held` — чтобы прототип демонстрировал разницу
между `total` и `available`. `EUR` намеренно нулевой — для проверки empty-state.

### 10.3 Курсы (mid) и дефолтная пара

Дефолтная пара при открытии экрана — **`RUB → USDT`** (BRD §3).

| Пара | rate (to за 1 from) | Человекочитаемо |
|------|--------------------|------------------|
| `RUB→USDT` | `0.010638297872` | 1 USDT = 94.00 RUB |
| `USDT→RUB` | `93.60` | 1 USDT = 93.60 RUB |
| `RUB→BTC` | `0.00000016` | 1 BTC ≈ 6 250 000 RUB |
| `USDT→BTC` | `0.0000150` | 1 BTC ≈ 66 667 USDT |
| `USDT→ETH` | `0.000410` | 1 ETH ≈ 2 439 USDT |
| `BTC→USDT` | `66200.00` | |
| `ETH→USDT` | `2420.00` | |
| `RUB→EUR` | `0.0098` | |

Спред между прямым и обратным курсом заложен намеренно: он показывает, что курсы
приходят из реального источника с bid/ask, а не вычисляются как `1/rate`.

#### Имитация движения рынка

Курсы в прототипе **не статичны**. К базовому курсу применяется коэффициент — один раз
за каждое истёкшее окно:

```
rate(t) = базовый курс × коэффициент ^ floor((t − старт сессии) / период окна)
```

| Параметр | Значение по умолчанию | Переопределение |
|----------|----------------------|-----------------|
| Коэффициент | `0.9995` (−0.05 % за окно) | `?rateTickFactor=0.99` |
| Период окна | `15 000 мс` — совпадает с TTL котировки (§2) | `?rateTickMs=3000` |
| Выключение | — | `?rateTick=off` |

**Зачем.** Без движения рынка автообновление по истечении TTL возвращало ровно то же число,
и пятнадцатисекундная фиксация выглядела декоративной: пользователь не мог понять, пересчиталась
котировка или таймер просто крутится. Теперь по истечении окна сумма получения действительно
меняется.

**Почему именно −0.05 %, а не больше.** Это **ниже** порога вмешательства 0.20 % из §11,
поэтому истечение TTL приводит к тихому пересчёту, а не к требованию заново принять условия.
Больший коэффициент превратил бы защитный механизм BRD §8 в шум, который пользователь
научится прокликивать не читая, и противоречил бы обещанию «обмен за несколько секунд» (BRD §2).
Случай сверх порога остаётся достижимым и демонстрируется отдельно — `?scenario=RATE_DRIFT`
(−0.53 %, требуется явное принятие) либо `?rateTickFactor=0.99`.

Накопление ограничено 400 окнами, чтобы вкладка, оставленная на ночь, не показывала абсурдный курс.

### 10.6 Сценарные переключатели прототипа

Чтобы демонстрировать негативные пути без бэкенда, прототип поддерживает сценарии.
Каждый соответствует сценарию Gherkin.

**Способ переключения — параметр URL:** `http://localhost:5173/?scenario=RATE_DRIFT`.
До 2026-08-07 сценарии переключались видимой dev-панелью под карточкой; заказчик попросил
её убрать, потому что прототип должен показывать страницу обмена, а не тестовую оснастку
вокруг неё. Параметр URL сохраняет возможность демонстрации и при этом не занимает места
на экране и не попадает в скриншоты.

| Ключ | Что имитирует | Ожидаемый код |
|------|---------------|---------------|
| `HAPPY` | нормальная работа | — |
| `RATE_DRIFT` | курс меняется через ~7 с после ввода | `RATE_CHANGED` (баннер) |
| `RATES_DOWN` | сервис курсов не отвечает | `RATE_SERVICE_UNAVAILABLE` |
| `EXCHANGE_DOWN` | сервис обмена не отвечает при submit | `EXCHANGE_SERVICE_UNAVAILABLE` |
| `KYC_PENDING` | верификация не завершена | `KYC_PENDING` |
| `LIMIT_HIT` | дневной лимит почти исчерпан | `LIMIT_EXCEEDED_DAILY` |
| `SCORING_REVIEW` | скоринг требует ручной проверки | `202 MANUAL_REVIEW` |
| `SLOW_NETWORK` | задержка 2.5 с на всех вызовах | демонстрация skeleton/loading |

### 10.7 Где отображаются балансы

Блок со списком балансов над формой убран по требованию заказчика от 2026-08-07.
Балансы теперь видны в двух местах:

1. **Строка `Available:` в шапке блоков «You Pay» и «You Receive»** — доступный баланс
   выбранного актива, виден без каких-либо действий. При ненулевом `held` рядом выводится
   `· 0.10 on hold`, иначе кейс ETH из §10.2 исчезал бы с экрана.
2. **Выпадающий список выбора актива** — полный перечень активов с доступными балансами,
   пометкой заблокированных средств и `No funds` у нулевого баланса.

Требование BRD §4 «просматривать доступные балансы» этим закрыто. Цена решения: чтобы увидеть
все пять балансов сразу, теперь нужно открыть список — регресс discoverability, зафиксированный
в UX-спецификации как риск R-16.

## 11. Нефункциональные требования

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| TTL котировки | 15 с | BRD §4 |
| Порог дрейфа курса | 0.20 % | Меньше — пользователя дёргает шум; больше — система несёт риск |
| Таймаут S5 (rates) | 800 мс | Пользователь ждёт котировку синхронно |
| Таймаут S1/S2/S3/S4 | 1 000 мс | Кешируются, вызываются параллельно |
| Таймаут S6 (accounting) | 1 500 мс | Финансовая операция, ретрай опасен |
| Таймаут S8 (order) | 2 000 мс | Запись, идемпотентна |
| Ретраи | Только для идемпотентных `GET`: 2 попытки, экспоненциальный backoff + jitter | Ретрай `POST` без идемпотентности = двойное списание |
| Circuit breaker | Порог 50 % ошибок на окне 20 запросов, open 30 с | Защита от каскадного отказа |
| Бюджет latency `POST /exchange-orders` | p95 ≤ 900 мс, p99 ≤ 2 000 мс | «Обмен за несколько секунд» (BRD §2) |
| Бюджет latency `POST /v1/exchange/quotes` | p95 ≤ 300 мс | Пересчёт при каждом вводе |
| Дебаунс ввода на клиенте | 300 мс | Баланс между «мгновенно» и нагрузкой |
| Доступность экрана обмена | 99.9 % | Внутренний модуль, не платёжный шлюз |

### Кеширование

| Данные | TTL | Стратегия при недоступности источника |
|--------|-----|----------------------------------------|
| Список активов и пар | 5 мин | отдаём устаревший (stale-while-revalidate) |
| Схема комиссий | 60 с | отдаём устаревший |
| KYC-статус | 30 с | **не** отдаём устаревший — блокируем |
| Балансы | не кешируется | всегда свежие |
| Курсы | 1 с | отдаём с `degraded: true` до 10 с, дальше `503` |
