# API Design — обоснование контракта Exchange BFF

> **Статус:** пояснительный (не нормативный).
>
> Нормативные источники: `../00-canonical-model.md` — домен, деньги, каталог ошибок,
> цепочка проверок; `exchange-orders.openapi.yaml` — машиночитаемый контракт, отвечающий
> на вопрос **что** передаётся; `INTEGRATIONS.md` — контракты девяти внешних систем.
>
> **Назначение документа.** Отвечает на вопрос **почему** контракт устроен именно так.
> Создан по решению **O-13** (`../../promtlog.md` §23): в спецификации на 3650 строк
> значительную часть занимала проза внутри `description`. Такая спецификация нечитаема
> инструментами (Swagger UI разворачивает эссе вместо описания поля), недиффабельна
> на ревью (правка формулировки выглядит как правка контракта) и провоцирует расхождение
> с каноном, потому что одно и то же правило записано в трёх местах.
>
> **Правило разрешения расхождений.** Спецификация старше этого документа; канон старше
> обоих. Расхождение — дефект, а не альтернативная трактовка.
>
> **Трассируемость.** Реестр требований, матрица покрытия и классификация изменений —
> `../10-api-requirements.md`. Каждый раздел ниже помечен идентификаторами требований
> `API-REQ-NN`, которые он объясняет.

## 1. Модель `quote → order`

*Объясняет: API-REQ-01, API-REQ-02, API-REQ-03, API-REQ-16, API-REQ-24.*

### 1.1 Почему две фазы, а не одна

Создание заявки — двухфазный процесс:

1. `POST /v1/exchange/quotes` — сервер фиксирует курс, комиссию и обе суммы, возвращает
   `quoteId` и `expiresAt` (**TTL 15 секунд**, канон §2). Котировка — отдельный ресурс,
   читается через `GET /v1/exchange/quotes/{quoteId}`. Построение котировки **не
   резервирует средства**, не расходует лимиты и не вызывает скоринг.
2. `POST /v1/exchange-orders` — клиент подтверждает **конкретную** котировку по `quoteId`.

Одношаговый вариант («передай сумму и создай заявку») внешне короче, но обязывает сервер
принять решение по курсу, которого пользователь не видел. BRD §2 требует, чтобы
пользователь понимал курс, сумму списания, сумму получения и комиссию **до**
подтверждения; BRD §4 требует показать «время фиксации курса». Оба требования
предполагают существование зафиксированного расчёта как самостоятельной сущности
со сроком жизни — это и есть котировка.

Цена решения: дополнительный round-trip и необходимость хранилища котировок с TTL
(SDD, ADR-02 и ADR-11).

**Почему `POST`, а не `GET`, для котировки.** Котировка — создаваемый ресурс
с идентификатором, сроком жизни и однократным расходованием. `GET` с параметрами
не даёт ни `Location`, ни возможности пометить котировку `CONSUMED`. Ответ — `201 Created`
с заголовком `Location`.

### 1.2 Зачем дублировать `expectedToAmount` и `expectedRate`

Клиент присылает не только `quoteId`, но и то, **что он показал пользователю**. Сервер
пересчитывает всё заново и сравнивает.

Дублирование выглядит избыточным ровно до первого инцидента, когда клиент показал одну
сумму, а сервер списал другую: без него расхождение проходит тихо, с ним превращается
в детерминированный `QUOTE_MISMATCH` (409) с серверными значениями в `params`.

Сравнение `fromAmount` ведётся **посимвольно после нормализации** (удаление незначащих
нулей): `"10000.00"` и `"10000.0"` эквивалентны, `"10000.01"` — нет.

`expectedFeeAmount` необязательно, но настоятельно рекомендуется: комиссия — самая частая
причина претензии «ожидал одно, списали другое», а строка `Fee` в сводке обязательна
по Design Brief.

### 1.3 Направление расчёта: сторона `side` (O-9)

*Объясняет: API-REQ-24.*

Исходно `POST /v1/exchange/quotes` принимал только `fromAmount` — сумму списания.
Обоснование было «поле „Получаю“ read-only по BRD §7, не поддерживаем то, чего нет
в интерфейсе». Обоснование неверно по существу: контракт API живёт дольше одного экрана,
и первый же запрос «хочу получить ровно 100 USDT» становится ломающим изменением.

Решение O-7…O-9 вводит в запрос котировки признак стороны:

| `side` | Что задаёт клиент | Что считает сервер |
|--------|-------------------|--------------------|
| `SELL` (по умолчанию) | `fromAmount` — сумму списания | `feeAmount`, `netFromAmount`, `toAmount` |
| `BUY` | `toAmount` — желаемую сумму получения | `netFromAmount`, `feeAmount`, `fromAmount` |

`side: SELL` по умолчанию — это ровно текущее поведение, поэтому изменение
**совместимое** (см. `../10-api-requirements.md` §8).

**Скоуп:** реализуется только в контракте. UI по BRD §7 оставляет поле «Получаю»
read-only, прототип использует исключительно `side: SELL`. Заложить поле сейчас дешевле,
чем выпускать `/v2` позже.

Разбор округления при `side: BUY` — §3.4. Это самое опасное место решения O-9.

### 1.4 Что клиент видит до появления котировки

BRD §3 требует получать актуальные курсы **при открытии экрана**, а не после ввода
суммы. Котировка при этом не существует: суммы ещё нет. Поэтому `GET /v1/exchange/pairs`
отдаёт `indicativeRate` — «ценник, а не обещание».

Различие нормативно: `indicativeRate` не годится для расчёта и не является
обязательством; обязывающий курс существует только внутри котировки с `quoteId`
и `expiresAt`. Смешивать их на экране нельзя — при одновременном показе двух цен
пользователь не знает, какая из них будет применена.

Пропуск этого различия в первой редакции стал причиной дефектов R-18/R-19
(«не подтягиваются курсы», «не получается обмен») — разбор в `../../promtlog.md` §14.

### 1.5 Жизненный цикл котировки

| `QuoteStatus` | Значение | Что делает клиент |
|---------------|----------|-------------------|
| `ACTIVE` | можно подтверждать | показывает обратный отсчёт до `expiresAt` |
| `EXPIRED` | истекла по времени | баннер «Rate expired», перезапрос котировки |
| `CONSUMED` | израсходована созданной заявкой | ведёт пользователя на существующую заявку |

Истёкшая котировка возвращается методом `GET` ещё **5 минут** именно ради различия
`EXPIRED` и `404`: это разные баннеры. По истечении окна хранения — `404 QUOTE_NOT_FOUND`.

Клиент строит обратный отсчёт от `expiresAt`, а **не** от локального таймера: иначе
расхождение часов клиента и сервера даёт отказ на видимо ещё живой котировке
(FM-13 в SDD).

Котировка другого пользователя возвращает `404`, а не `403`: существование чужого
`quoteId` не должно быть наблюдаемым.

### 1.6 Пары направленные, обратный курс не равен `1/rate`

`RUB→USDT` и `USDT→RUB` конфигурируются независимо: разные комиссии, разные лимиты,
независимый признак включения. Спред между прямым и обратным курсом заложен намеренно
(канон §10.3) — он показывает, что курс приходит из источника с bid/ask, а не
вычисляется делением.

`inverseRate` в ответе — **только для отображения** (`ROUND_HALF_UP`, 2 знака):
«1 USDT = 94.00 RUB» читается человеком легче, чем «1 RUB = 0.010638297872 USDT».
В расчётах не участвует.

### 1.7 Компенсация hold → order

Резерв средств (шаг 18 канона §6) создаётся **до** регистрации заявки в S8 (шаг 19).
Если шаг 19 провалился, BFF обязан снять hold компенсирующим `DELETE /v1/holds/{holdId}`
в S6. Если компенсация тоже не прошла — событие уходит в очередь компенсаций; у hold
есть собственный `expiresAt` и он снимется по таймауту как последняя линия защиты.
Пользователю в обоих случаях возвращается `500 ORDER_CREATION_FAILED`
с `retryable: true`.

Обратный порядок (сначала заявка, потом резерв) дал бы заявку без обеспечения — это хуже,
чем повисший резерв, который снимется сам.

## 2. Идемпотентность

*Объясняет: API-REQ-04, API-REQ-05, API-REQ-06, API-REQ-25.*

### 2.1 Почему заголовок обязателен, а не рекомендован

`POST /v1/exchange-orders` требует `Idempotency-Key` (UUIDv4). Запрос без заголовка
отклоняется `400 VALIDATION_ERROR` **до** любых бизнес-проверок.

Без ключа ретрай при таймауте означает двойное списание. Финансовая мутация, для которой
повтор небезопасен, но неизбежен (сеть рвётся), не может опираться на дисциплину клиента.

### 2.2 Гранулярность ключа

Ключ генерируется клиентом **один раз на попытку пользователя** — одно нажатие
«Обменять» — и переиспользуется при сетевых ретраях **этого же** нажатия. Новая попытка
(новая котировка, изменённая сумма) — новый ключ.

Слишком широкая гранулярность (ключ на сессию) склеила бы две разные заявки в одну;
слишком узкая (ключ на каждый HTTP-запрос) не защитила бы ни от чего.

### 2.3 Окно хранения и поведение при повторе

Окно — **24 часа** (канон §9). Ключ хранится вместе с хешем канонизированного тела:

| Ситуация | Ответ |
|----------|-------|
| Повтор с **тем же** телом | тот же `201`/`202`, тот же `orderId`, заголовок `X-Idempotent-Replay: true` |
| Повтор с **другим** телом | `409 IDEMPOTENCY_CONFLICT`, `retryable: false` |
| Параллельный повтор, первый запрос ещё в обработке | `409 IDEMPOTENCY_CONFLICT`, `retryable: true` + `Retry-After` |

### 2.4 Ключ занимается до начала работы

Ключ занимается **до** первой бизнес-проверки, а не после успеха, и освобождается при
отказе. Занятие после успеха оставляло окно, в которое два параллельных запроса с одним
ключом проходили цепочку одновременно и создавали две заявки. Это была находка
Code Reviewer (`../../promtlog.md` §13, раздел Major) — контракт был прав, реализация нет.

Отличие от `QUOTE_ALREADY_USED`: там конфликтует **котировка**, здесь — **ключ**.
Типичный источник `QUOTE_ALREADY_USED` — двойной клик, при котором клиент сгенерировал
два разных ключа на одну котировку.

### 2.5 Таймаут не означает «не выполнено»

`504 UPSTREAM_TIMEOUT` на мутирующем вызове не означает, что мутация не произошла.
Перед возвратом ошибки BFF выполняет сверку по ключу идемпотентности в S8
(`GET /v1/orders?idempotencyKey=…`) и, если заявка нашлась, возвращает её как успех.
Ретрай `POST` в S8 при таймауте **запрещён**.

Это опирается на **блокирующее допущение** ASSUMPTION-03/04 (`../../promtlog.md` §9):
идемпотентность и поиск по ключу должны существовать на стороне S6 и S8. Без них
корректная обработка таймаута финансовой мутации невозможна в принципе — см. OPEN-7.

### 2.6 Восстановление состояния клиентом (O-10)

*Объясняет: API-REQ-25.*

Клиент, потерявший соединение сразу после `POST`, не знает `orderId` и не может
ни показать результат, ни безопасно повторить. Ретрай с тем же ключом решает это
частично: он работает, пока клиент помнит ключ, но не после перезагрузки страницы.

Решение O-10: `GET /v1/exchange-orders?idempotencyKey=…` — поиск **одной** заявки
по ключу.

Это **не история операций** (она вне скоупа по канону §1): фильтр по ключу обязателен,
запрос без него — `400 VALIDATION_ERROR`, ответ содержит одну заявку или `404`. Границу
надо держать явно, иначе эндпоинт незаметно превратится в листинг.

Цена: поиск по ключу — вектор перебора. Ключ UUIDv4 (122 бита энтропии), но эндпоинту
нужен отдельный rate limit, более строгий, чем общий `GET`-бюджет; заявки другого
пользователя возвращают `404`, а не `403`.

## 3. Деньги и округление

*Объясняет: API-REQ-07, API-REQ-08, API-REQ-09.*

### 3.1 Почему все денежные величины — строки

Все суммы и курсы передаются как **строки** с десятичной записью (`"25450.00"`,
`"0.010638297872"`). `number` в денежных полях запрещён на всём пути: JSON, BFF,
состояние фронтенда, отображение.

Причины: IEEE-754 не представляет `0.1` точно; в JSON-числе `25450.00` неотличимо
от `25450`, и различие «два знака или ноль знаков» — это различие валют, а не
форматирования. Клиент обязан работать с этими значениями через `decimal.js` либо
целочисленные minor units.

Нормативная регулярка — канон §5.1. Спецификация повторяет её в `DecimalString.pattern`,
потому что там она исполняемая, а не описательная.

### 3.2 Порядок расчёта и правила округления

**Нормативный источник — канон §5.3 (порядок) и §5.4 (режимы округления). Здесь
не дублируется.**

Кратко для навигации: комиссия удерживается внутри введённой суммы
(`INCLUDED_IN_SOURCE`), считается от `fromAmount`, округляется **вверх** до
`decimals(fromAsset)`; сумма получения считается от `netFromAmount` и округляется
**вниз** до `decimals(toAsset)`. Инварианты I1…I5 — канон §5.4.

Клиент **не пересчитывает** суммы для отображения итога: он показывает то, что вернул
сервер. Иначе на границе округления UI и сервер разойдутся в последнем знаке — и
пользователь увидит два разных числа для одной операции.

### 3.3 Почему режим комиссии — enum из одного значения

`FeeMode` содержит единственное значение `INCLUDED_IN_SOURCE`. Это не заготовка
«на будущее», а фиксация решения C-06 (`../../promtlog.md` §3): при режиме `ON_TOP`
кнопка `MAX` и чип `100 %` всегда приводили бы к `INSUFFICIENT_FUNDS`, потому что
`fromAmount + fee > available`, то есть требования BRD §4 и Design Brief стали бы
нереализуемыми.

Поле сохранено в контракте, чтобы режим можно было сделать конфигурируемым без
ломающего изменения. Цена решения названа в каноне §5.3: пользователь получает меньше,
чем «сумма × курс», поэтому строка `Fee` в сводке обязательна и не может быть скрыта.

### 3.4 Округление при обратном расчёте (`side: BUY`)

Решение O-9 создаёт вторую сторону расчёта, и правило «`toAmount` округляется **вниз**»
перестаёт быть безусловно верным: при `side: BUY` `toAmount` задан пользователем и
округлять его некуда — округляется `fromAmount`, а его округление вниз работает
**в пользу** пользователя и против системы.

Вопрос закрыт решением **O-15**: округление задаётся **ролью** стороны, а не именем
величины. Заданная пользователем сторона не округляется вовсе, производная округляется
в пользу системы. Нормативная формулировка — канон §5.4, разбор — `docs/SDD.md` §3.1.

| Величина при `side: BUY` | Режим | Почему |
|--------------------------|-------|--------|
| `toAmount` | как задан клиентом, проверяется `decimals(toAsset)` | это вход, а не результат |
| `netFromAmount` = `toAmount / rate` | `ROUND_UP` до `decimals(fromAsset)` | система не выдаёт больше, чем получила |
| `feeAmount` | `ROUND_UP` до `decimals(fromAsset)` | как в §5.4 канона |
| `fromAmount` = `netFromAmount + feeAmount` | точное сложение | сохраняет инвариант I1 |

Инвариант I2 (`toAmount ≤ netFromAmount × rate`) при этом выполняется автоматически,
а не проверяется задним числом. Правило нормативным **не является** до внесения
в канон §5.4 — это открытый вопрос, см. `../10-api-requirements.md` §7.

### 3.5 Почему `networkFee` всегда `"0"`

Обмен внутренний: активы перемещаются между балансами одного кошелька, ончейн-транзакций
нет (канон §5.5). Поле и строка `Network` в сводке сохранены, потому что сеть получения
(`USDT@TRON` против `USDT@ETHEREUM`) определяет реальную стоимость будущего **вывода** —
пользователь должен видеть выбор уже на обмене.

`USDT@TRON → USDT@ETHEREUM` — это не обмен, а перевод между сетями; он вне скоупа
и отклоняется как `SAME_ASSET_PAIR`.

## 4. Семантика дрейфа курса

*Объясняет: API-REQ-10, API-REQ-22, API-REQ-23.*

### 4.1 Порог дрейфа — параметр пары (O-8)

*Объясняет: API-REQ-23.*

Порог был единым: **0.20 %** для всех пар. Значение разумно для `RUB→USDT`, но для
`RUB→BTC` собственная волатильность актива превышает порог почти на каждом
подтверждении — защитный механизм превращается в шум, который пользователь научится
прокликивать не читая.

Решение O-8: порог — **параметр пары**, приходит от S4 (`driftThresholdPercent`
в конфигурации пары), значение по умолчанию **0.20 %**.

Контракт:

- `GET /v1/exchange/pairs` отдаёт порог **на каждую пару** (`ExchangePair.driftThresholdPercent`);
  прежнее глобальное поле `PairsResponse.rateDriftThresholdPercent` сохраняется как
  значение по умолчанию для пар, у которых собственный порог не задан;
- `params.thresholdPercent` в `RATE_CHANGED` возвращает **фактически применённый** порог,
  а не константу — UI объясняет отказ теми же числами, которыми считал сервер.

Цена: порог начинает зависеть от внешнего сервиса. При недоступности S4 применяется
дефолт 0.20 % и котировка помечается `degraded` — но **не** отказ: неизвестный порог
нельзя считать бесконечным, и нельзя блокировать обмен из-за отсутствия параметра,
у которого есть безопасное значение.

### 4.2 Согласие выражается в суммах, а не в курсе (O-7 → O-16)

*Объясняет: API-REQ-22.*

Было: `acceptRateChange: boolean`. Семантика — «согласен на дрейф в пределах порога»;
дрейф сверх порога возвращал `RATE_CHANGED` независимо от флага.

Дефект конструкции назвал сам автор контракта (`../../promtlog.md` §9, самокритика №1):
булев флаг не выражает «насколько хуже я готов принять». У пользователя есть только два
варианта — «в пределах порога, который выбрал не я» или «спрашивай каждый раз». Согласие
без названной границы не является информированным.

**Первое решение (O-7) вводило `maxAcceptableRate` и было отменено.** Архитектор показал,
что в принятой записи курса это ловушка: `rate` — единиц `toAsset` за 1 единицу
`fromAsset`, значит ухудшение для пользователя означает **уменьшение** `rate`, и защитой
служит нижняя граница, а имя `max…` читается как верхняя. Буквальная реализация по имени
сняла бы защиту BRD §8 целиком и молча (`docs/SDD.md` §23.1, дефект D-15).

**Действующее решение — O-16.** Чинить имя границы курса значило лечить симптом:
пользователь принимает решение не по курсу, а по **сумме**, и именно сумму он видит на
экране. Поэтому согласие выражается в той же единице и симметрично режиму расчёта:

| Режим (`side`) | Что задал пользователь | Поле согласия | Смысл |
|----------------|------------------------|---------------|-------|
| `SELL` | сумму списания | `minAcceptableToAmount` | «не зачисляйте меньше, чем X» |
| `BUY` | сумму получения | `maxAcceptableFromAmount` | «не списывайте больше, чем Y» |

Ровно одно из двух полей допустимо, и допустимо именно то, которое относится к
**производной** стороне. Второе — `VALIDATION_ERROR`. Поле необязательное.

Правило применения на шаге 10 цепочки:

| Условие | Исход |
|---------|-------|
| Поле задано, пересчитанная сумма не хуже границы | заявка создаётся по живому курсу |
| Поле задано, пересчитанная сумма хуже границы | `409 RATE_CHANGED` |
| Поле не задано, дрейф `≤` порога пары | заявка создаётся |
| Поле не задано, дрейф `>` порога пары | `409 RATE_CHANGED` |

Сверка ведётся с **пересчитанной суммой**, а не с курсом: направление сравнения тогда
невозможно перепутать — «меньше зачислили» и «больше списали» одинаково плохи и одинаково
очевидны. Ответ `201` обязан вернуть фактический курс исполнения и фактические суммы,
иначе пользователь знает только границу, но не результат.

Верхняя граница самого согласия **сохраняется**: значение, отличающееся от котировки
больше чем на `maxDriftCap`, отклоняется как `VALIDATION_ERROR`. Согласие «на любой курс»
контрактом не предусмотрено и не должно быть: подписать неограниченный проскок
пользователь не может осознанно. Величина `maxDriftCap` — открытый вопрос
(провизорно 2 %), см. `../10-api-requirements.md` §7.

Цена решения, названная явно: два поля вместо одного. Контракт шире ради того, чтобы
границу нельзя было прочитать в обратную сторону.

`acceptRateChange` сохраняется как `deprecated` на время миграции и **игнорируется**.
План депрекации — минимум 90 дней, заголовки `Deprecation` / `Sunset`,
см. `../10-api-requirements.md` §8.

### 4.3 `RATE_CHANGED` против `QUOTE_MISMATCH`

Оба кода — `409`, и их путают. Различие:

| Код | Что разошлось | Виновник | Что делает клиент |
|-----|---------------|----------|-------------------|
| `QUOTE_MISMATCH` | присланное клиентом ↔ сохранённая котировка | клиент показал не то, что зафиксировал сервер | перерисовывает сводку по серверным значениям и просит подтвердить |
| `RATE_CHANGED` | сохранённая котировка ↔ **живой** курс | рынок | показывает «было → стало» и просит принять новые условия |

`QUOTE_MISMATCH` — признак дефекта клиента или гонки в его состоянии; `RATE_CHANGED` —
штатное событие. Отсюда разные тексты: «Details changed. Please confirm again.» против
«Rate changed. Calculation updated.» (BRD §8 требует именно второго).

Порядок проверок нормативен: шаг 9 (`QUOTE_MISMATCH`) идёт **раньше** шага 10
(`RATE_CHANGED`). Сначала убеждаемся, что стороны говорят об одном расчёте, и только
потом — что этот расчёт ещё актуален.

### 4.4 Что обязательно в payload `RATE_CHANGED`

`params` содержит `quotedRate`, `currentRate`, `quotedToAmount`, `currentToAmount`,
`driftPercent`, `thresholdPercent` и `newQuoteId`.

Обе **суммы** обязательны вместе с курсами: пользователь принимает решение по сумме,
а не по коэффициенту, и заставлять его пересчитывать разницу в уме на экране
с 15-секундным таймером недопустимо. В первой редакции контракта этих полей не было
вовсе, а payload описывался тремя разными способами — блокер B-6 Code Reviewer
(`../../promtlog.md` §13).

`newQuoteId` отдаётся при `QUOTE_EXPIRED` и `RATE_CHANGED`, чтобы клиент обновил сводку
одним ответом, без дополнительного round-trip.

**Дрейф детектируется не только при подтверждении.** Сравнение курса выполняется и при
автообновлении котировки по истечении TTL, иначе сумма меняется под курсором молча,
а кнопка остаётся активной — блокер B-2, из-за которого главное требование BRD §8
не выполнялось.

## 5. Цепочка проверок и почему комплаенс раньше баланса

*Объясняет: API-REQ-11, API-REQ-12.*

**Нормативный источник — канон §6. Полная таблица 19 шагов здесь не дублируется.**

Три свойства цепочки, которые контракт обязан сохранять:

1. **Порядок нормативен.** Он делает ошибку детерминированной, когда нарушено несколько
   условий одновременно. Иначе один и тот же запрос давал бы разные коды в зависимости
   от того, какой сервис ответил первым, и приёмочный сценарий проверял бы порядок
   вызовов вместо правила.
2. **Fail-fast.** Первая непройденная проверка прекращает обработку. Собирать все
   нарушения в один ответ здесь вредно: это раскрывает больше состояния, чем нужно.
3. **Compliance First.** Шаги 13–16 (пользователь и кошелёк → KYC → лимиты → скоринг)
   идут **перед** проверкой баланса (17).

Обоснование Compliance First — не «так принято», а конкретный вектор: если
неверифицированный пользователь получает `INSUFFICIENT_FUNDS` при одной сумме и
`LIMIT_EXCEEDED_DAILY` при другой, он подбором сумм восстанавливает и баланс, и остаток
лимита. Различие текстов ошибок — канал утечки.

Цена решения названа в каноне §6: пользователь с недостатком средств и незавершённым KYC
увидит сначала сообщение про KYC. Это приемлемо, потому что KYC блокирует его в любом
случае, а порядок сообщений не меняет исход.

**Клиентская предвалидация** (шаги 1, 4, 11, 12, 17 и дневной лимит) выполняется
в прототипе inline и немедленно — ради скорости отклика. Она **не заменяет** серверную
и **не является контрактом**: сервер прогоняет всю цепочку заново. Ошибки уровня поля,
пришедшие от сервера, живут в отдельном слоте состояния и не стираются локальным
пересчётом — блокер B-4.

## 6. Каталог ошибок

*Объясняет: API-REQ-13, API-REQ-14, API-REQ-15, API-REQ-26.*

### 6.1 Как выбирается код

**Нормативный источник — канон §7: перечень кодов, HTTP-статусы, `retryable`, место
крепления в UI и текст для пользователя. В спецификации живёт `enum ErrorCode`,
в этом документе — правила выбора.**

1. Код определяется **шагом цепочки** §6, на котором произошёл отказ. Один шаг — один
   код (кроме шагов 13 и 14, где различаются причины).
2. Класс HTTP определяется природой отказа, а не удобством: `400` — клиент собрал запрос
   неправильно; `422` — запрос правильный, но так нельзя; `409` — конфликт состояния;
   `403` — запрещено по соответствию; `404` — не существует **или не видно этому
   пользователю**; `429`/`503`/`504` — инфраструктура.
3. Ошибки внешних систем **маппятся** в коды каталога на границе BFF. Наружу не уходит
   ни один код внешнего вендора. Таблица маппинга — `INTEGRATIONS.md`, разделы `*.5`.
4. Перечень **закрыт**: код вне enum приложением не порождается. Обнаружив ситуацию без
   кода, её выносят в решение СТО, а не затыкают ближайшим подходящим кодом — так был
   ратифицирован `ORDER_NOT_FOUND` (решение O-1).

### 6.2 Почему RFC 9457 расширен полем `code`

Чистый RFC 9457 предлагает ветвиться по `type` (URI). URI неудобен как ключ в `switch`
на клиенте и провоцирует опечатки, которые не ловятся типами. `code` из закрытого enum
решает это; `type` сохранён для совместимости и как ссылка на документацию.

`title` и `detail` — **не контракт**: локализуемы, меняются без версионирования.
Фронтенд ветвится только по `code`. `detail` диагностический, для разработчика и логов,
и не показывается пользователю как есть — текст для пользователя собирается клиентом
по `code` и `params`.

### 6.3 Почему `ProblemParams` открыт (`additionalProperties: true`)

Набор ключей `params` зависит от `code`. Строго это выражается через 29 подсхем
с `oneOf` и `discriminator` — и такая спецификация становится нечитаемой для человека,
который ищет, что приходит при `RATE_CHANGED`.

Компромисс назван явно (`../../promtlog.md` §9, самокритика №6): строгость принесена
в жертву читаемости. Следствия, которые контракт обязан компенсировать:

- клиент обязан переносить **отсутствие** ожидаемого ключа без падения — показать
  сообщение без подстановки;
- денежные значения в `params` — тоже строки; ошибка не повод переключаться на `number`;
- персональные данные в `params` **запрещены**: тело ошибки попадает в клиентские логи
  и в системы мониторинга;
- `params.service` (какая внешняя система отказала) отдаётся клиенту намеренно: имена
  внутренних сервисов не секрет, а без них диагностика инцидента по обращению
  пользователя невозможна.

### 6.4 Почему `SCORING_REVIEW_REQUIRED` — не ошибка

Код числится в каталоге §7, но приходит **не** в конверте `ProblemDetails`. Он
возвращается с `202 Accepted` в поле `review.code` успешного тела `ExchangeOrder`
со статусом `MANUAL_REVIEW`.

Причина: это альтернативный **успешный** исход. Заявка принята, средства
зарезервированы, решение принимает комплаенс в течение `review.slaHours`. Подать это
ошибкой означало бы, что клиент по общему обработчику ошибок откатит экран и потеряет
`orderId` уже существующей заявки.

Средства при `MANUAL_REVIEW` остаются зарезервированными: отпустить их до решения
комплаенса значит сделать решение неисполнимым.

### 6.5 Почему у `404` на заявке отдельная схема

`ProblemDetailsOrderNotFound` — суженный вариант `ProblemDetails` с `const` на `status`
и `code`. На этом ответе никакой другой код невозможен, и контракт это выражает вместо
«одного из тридцати возможных кодов».

История кода: каталог §7 изначально не содержал кода для ненайденной заявки
(`QUOTE_NOT_FOUND` — про котировку, `VALIDATION_ERROR` привязан к `400`). API Architect
вынес пробел наверх вместо подстановки неточного кода; СТО ратифицировал
`ORDER_NOT_FOUND` (решение O-1).

### 6.6 Почему `RATE_SERVICE_UNAVAILABLE` отделён от `EXCHANGE_SERVICE_UNAVAILABLE`

Оба — `503`. Разделение существует потому, что у отказа курсов свой UX: экран остаётся
живым, суммы не пересчитываются, кнопка блокируется с текстом-причиной — это не «всё
сломалось». `EXCHANGE_SERVICE_UNAVAILABLE` — обобщённый отказ любой другой блокирующей
системы (S1, S2, S3, S4, S6, S8); конкретная указана в `params.service`.

Наблюдаемое пользователем поведение у этих двух кодов местами совпадает — поэтому
Business Analyst сознательно не покрыл `EXCHANGE_SERVICE_UNAVAILABLE` отдельным
Gherkin-сценарием (`../../promtlog.md` §5). Различие кодов — предмет контракта, а не
приёмочного сценария.

### 6.7 Почему в `500` нет технических деталей

Тело `500` не содержит стек-трейсов, имён классов и SQL. Диагностика ведётся
по `correlationId`, который есть в каждом ответе и в каждой ошибке.

### 6.8 `LIMIT_EXCEEDED_YEARLY` (O-12)

*Объясняет: API-REQ-26.*

S4 реально возвращает годовое превышение. В первой редакции оно схлопывалось
в `LIMIT_EXCEEDED_MONTHLY`, и пользователь видел сообщение про **не то окно**: «Monthly
limit reached» при исчерпанном годовом лимите — это ложь в UI, из которой пользователь
делает неверный вывод («подожду до первого числа»).

O-12 добавляет `YEARLY` в `LimitPeriod` и `LIMIT_EXCEEDED_YEARLY` в каталог. Внесено СТО
до запуска агентов — в канон §7, в enum спецификации и в `ERROR_CATALOG` прототипа.
Изменение **совместимое**: новое значение в enum ответа, клиент обязан переносить
неизвестный код (показать общий текст).

## 7. Сквозные соглашения

*Объясняет: API-REQ-17, API-REQ-18, API-REQ-19, API-REQ-20, API-REQ-27.*

### 7.1 Версионирование

Версия в пути: `/v1`. Ломающее изменение = новый major и новый путь `/v2`.

| Ломающее | Совместимое |
|----------|-------------|
| удаление поля ответа | добавление поля ответа |
| сужение типа или ограничения | расширение ограничения |
| новый **обязательный** параметр запроса | новый **необязательный** параметр запроса |
| изменение семантики кода ошибки | новое значение в enum **запроса** |
| удаление значения из enum ответа | новое значение в enum **ответа** (при условии ниже) |

Условие для enum ответа: клиент обязан обрабатывать неизвестные значения. Для
`OrderStatus` — как «неизвестный, **не терминальный**, продолжать опрос»; для
`ErrorCode` — как общий текст ошибки. Поэтому `OrderStatus` содержит статусы за границей
скоупа (`EXECUTING`, `COMPLETED`, `FAILED`, `EXPIRED`): клиент, написанный сейчас,
не должен сломаться, когда исполнение заявки выйдет за пределы этого проекта.
Внутренний статус `VALIDATING` наружу не отдаётся никогда и в enum отсутствует.

Депрекация — минимум **90 дней**, заголовки `Deprecation` и `Sunset`
(RFC 9745 / RFC 8594).

### 7.2 Rate limiting

Все ответы несут `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`.
Превышение → `429 RATE_LIMITED` с обязательным `Retry-After`: клиент без него уйдёт
в busy-loop и усугубит перегрузку.

Бюджеты на пользователя: `POST /v1/exchange/quotes` — 60/мин (клиентский дебаунс 300 мс
делает это достижимым только при аномальной активности); `POST /v1/exchange-orders` —
10/мин; `GET`-эндпоинты — 120/мин. Для `GET /v1/exchange-orders?idempotencyKey=…`
нужен отдельный, более строгий бюджет — см. §2.6.

Отдельно от лимитов частоты: автоматических ретраев упавшего сервиса в прототипе нет,
восстановление — явное действие пользователя. Опрос упавшего сервиса ~3 запроса/с был
находкой ревью (`../../promtlog.md` §13, Major).

### 7.3 Бюджеты задержки

`POST /v1/exchange-orders`: p95 ≤ 900 мс, p99 ≤ 2000 мс. `POST /v1/exchange/quotes`:
p95 ≤ 300 мс. Значения — канон §11.

Бюджет несовместим с последовательной суммой таймаутов внешних систем, поэтому
параллельный фан-аут и кеши **обязательны**, а не оптимизация; остаточный риск
зафиксирован как FM-11 в SDD (расхождение A-3).

Превышение бюджета вышестоящей системой → `504 UPSTREAM_TIMEOUT`; полный отказ → `503`.

### 7.4 Корреляция

`X-Correlation-Id` (ULID, 26 символов Crockford Base32) принимается от клиента,
генерируется сервером при отсутствии, возвращается **в каждом ответе и в каждой ошибке**
и дублируется в теле `ProblemDetails.correlationId`.

Дублирование в теле не избыточно: заголовки теряются в клиентских логах и в скриншотах
от пользователей, а `correlationId` — единственный способ найти инцидент по обращению.

### 7.5 Аутентификация — и почему её нет в прототипе

В контракте описаны две схемы: `bearerAuth` (JWT, claim `sub` = `userId`, `scope` обязан
включать `wallet:exchange`) и `gatewayUserId` (`X-User-Id`, проставляемый API-gateway
после проверки JWT).

Приложение доверяет `X-User-Id` **только** потому, что gateway безусловно перезаписывает
его на входе из внешнего периметра. Заголовок, пришедший от клиента напрямую в обход
gateway, обязан отбрасываться — иначе это тривиальный обход авторизации.

**В прототипе аутентификация не используется** по прямому требованию заказчика
(`../../promtlog.md` §1, R-09): mock-сервер принимает запросы без `Authorization`,
`userId` зашит в фикстуры (канон §10.1). Схема оставлена в спецификации, чтобы контракт
был пригоден к передаче в разработку без переписывания; `security` содержит `{}` как
альтернативу именно для mock-сервера.

Следствие для `/v1/wallet/balances`: `wallet` — singleton-ресурс, идентификатор кошелька
в пути не принимается. Это нарушает формальное правило «ресурсы во множественном числе
с идентификатором», но снимает вектор IDOR — передавать чужой `walletId` некуда
(решение O-4).

### 7.6 Что запрещено передавать

`ClientMeta` — необязательный контекст клиента (канал, `deviceId`, локаль, версия
приложения), используемый скорингом S3 как сигналы. Ограничение нормативно:
персональные данные, токены, номера счетов и любые секреты сюда класть **запрещено**.
Поля попадают в S3 и в аналитику и не подлежат удалению по запросу пользователя как
часть аудиторского следа.

`deviceId` — псевдонимный непрозрачный токен, стабильный в пределах установки: **не**
IMEI, **не** серийный номер, **не** рекламный идентификатор.

### 7.7 Лимиты оборота: `resetsAt` и часовой пояс (O-11)

*Объясняет: API-REQ-27.*

Лимиты нормализуются в единую валюту (`RUB`) и учитываются по **UTC**-границе суток.
Для пользователя-резидента `AE` (канон §10.1) это означает сброс дневного лимита
в 04:00 по местному времени — цифра «Available today» меняется в момент, который
пользователь не может объяснить.

Бизнес-правило (UTC или локальное время резидента) остаётся открытым вопросом
к комплаенсу — OPEN-1. Решение O-11 меняет не правило, а **наблюдаемость** правила:

- `TurnoverLimitWindow.resetsAt` — момент обнуления окна (ISO-8601 UTC с мс);
- `TurnoverLimitWindow.resetTimeZone` — идентификатор IANA пояса, в котором окно
  рассчитано (`UTC` при текущем правиле);
- `params.resetAt` в `LIMIT_EXCEEDED_*` — то же значение для текста ошибки.

Без пояса `resetsAt` остаётся необъяснимой цифрой: клиент не может решить, показывать
её в местном времени пользователя или как есть. Цена решения: клиент обязан показывать
пояс, иначе поле бесполезно.

Учёт при этом остаётся в UTC — контракт перестаёт **скрывать** правило, но не меняет
его. Смена правила будет изменением поведения, а не контракта.
